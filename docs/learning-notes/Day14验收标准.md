# Day14 核心知识验收 : 全局异常处理

## 问题 1：为什么不能让每个路由自己处理所有异常？

如果每个路由都自行处理所有异常，会导致大量重复代码，增加维护成本，并且容易出现异常处理规则不一致的问题。

例如，多个路由都需要处理模型调用失败、结构化输出异常和未知异常。如果每个路由都编写一套 `try-except`，后续修改错误响应格式或状态码时，就需要修改多个地方。

因此，可以采用统一异常处理机制：

- **路由层**：接收请求、调用 Service 层，必要时处理当前接口特有的逻辑。
- **Service 层**：处理业务逻辑，根据业务情况抛出相应的自定义异常。
- **全局异常处理器**：集中捕获异常，将异常转换为统一的 HTTP 响应。

例如，FastAPI 可以通过 `@app.exception_handler()` 注册全局异常处理器，避免每个路由重复编写异常处理代码。

这种设计可以降低代码重复度，提高异常处理的一致性和可维护性。

## 问题 2：Pydantic 请求模型和响应模型分别解决什么问题？

Pydantic 请求模型和响应模型分别负责约束进入系统的数据和系统返回的数据。

### 请求模型

请求模型用于定义客户端提交的数据结构，并对请求参数进行校验。

例如：

```python
from pydantic import BaseModel, Field


class LogAnalyzeRequest(BaseModel):
    log_text: str = Field(min_length=1, max_length=1000)
```

它可以确保：

- 请求中包含必需的 `log_text` 字段。
- `log_text` 的类型符合要求。
- 日志内容长度在规定范围内。

当请求不符合模型定义时，FastAPI 通常会在执行路由函数之前返回 `422 Unprocessable Entity`。

### 响应模型

响应模型用于定义接口应该返回的数据结构，并对返回数据进行约束。

例如：

```python
from pydantic import BaseModel


class LogAnalyzeResponse(BaseModel):
    error_type: str
    root_cause: str
    solution: str
    confidence: float
```

它可以帮助开发者：

- 统一接口响应结构。
- 检查返回字段及其类型。
- 为接口文档生成提供依据。
- 降低返回数据不符合约定的风险。

在 FastAPI 中，可以通过 `response_model=LogAnalyzeResponse` 声明响应模型。

**总结：请求模型约束输入，响应模型约束输出。** 两者共同提高接口的数据规范性和可维护性。

## 问题 3：Structured Output 为什么仍然需要业务校验？

Structured Output 用于约束大模型按照指定的数据结构返回结果，例如 JSON 格式以及规定的字段。

但是，**结构合法不代表业务结果一定正确**。

例如，模型返回：

```json
{
  "error_type": "DatabaseConnectionError",
  "root_cause": "数据库连接失败",
  "solution": "检查数据库连接配置",
  "confidence": 0.95
}
```

这个 JSON 的格式可能完全正确，但仍然可能存在业务问题：

- `error_type` 不属于系统允许的故障类型。
- `confidence` 超出合理范围，例如返回 `1.5`。
- `root_cause` 与原始日志证据不一致。
- `solution` 为空，或者建议与故障类型不匹配。

因此，需要分层校验：

1. **格式校验**：检查返回内容是否为合法 JSON。
2. **结构校验**：通过 Pydantic 检查字段、类型及约束。
3. **业务校验**：检查故障类型、置信度、证据和解决建议是否符合业务规则。

例如：

```python
if not 0 <= result.confidence <= 1:
    raise StructuredOutputError("置信度超出允许范围")
```

需要注意，置信度在数值范围内，并不意味着它真实可靠；故障原因与日志证据是否一致，也可能需要额外规则或评估机制判断。

因此，Structured Output 只能降低输出格式不规范的问题，不能代替业务校验。

## 问题 4：API 层、Service 层、模型层分别负责什么？

三者的主要区别在于职责不同，目的是降低耦合，让代码更容易测试、维护和扩展。

### API 层

负责处理 HTTP 请求与响应，包括：

- 定义接口路径和请求方式。
- 接收请求参数。
- 使用请求模型校验输入。
- 调用 Service 层。
- 返回接口响应。

例如，FastAPI 中的 `@app.post()` 或 `@router.post()` 定义的路由函数通常属于 API 层。

### Service 层

负责实现具体业务逻辑，包括：

- 组织日志分析流程。
- 调用大模型服务。
- 处理模型返回结果。
- 执行业务校验。
- 根据业务情况抛出自定义异常。

Service 层不应过度依赖 HTTP 请求对象，以便在 API 接口之外复用业务逻辑。

### 模型层

在当前项目中，模型层主要负责定义数据结构，例如：

- `LogAnalyzeRequest`：请求数据模型。
- `LogAnalyzeResponse`：响应数据模型。
- `ErrorAnalysis`：大模型结构化分析结果模型。

这些模型通常通过 Pydantic 实现，用于约束字段、类型及部分校验规则。

### 三层协作流程

```text
客户端发送 HTTP 请求
        ↓
API 层：接收请求、参数校验
        ↓
Service 层：执行业务逻辑、调用大模型
        ↓
模型层：校验和组织结构化数据
        ↓
Service 层：业务校验并组织结果
        ↓
API 层：返回 HTTP 响应
        ↓
客户端接收结果
```

需要注意：模型层不是必须独立执行的一个处理阶段。Pydantic 模型可以在请求进入 API 层时校验，也可以在 Service 层处理模型输出时校验。

从 Java 开发的角度理解，可以将 API 层类比为 Controller，将 Service 层类比为 Service，将 Pydantic 模型类比为 DTO 或数据传输对象。

## 问题 5：为什么模型调用失败通常更接近 502，而不是 400？

HTTP 状态码应根据错误发生的原因确定。

- **400 Bad Request**：通常表示客户端请求本身不符合要求，例如请求格式错误或参数存在问题。
- **502 Bad Gateway**：通常表示当前服务作为网关或代理，从上游服务获得了无效响应。
- **500 Internal Server Error**：表示服务内部发生了未能正常处理的意外错误。

在日志分析器中，客户端提交合法日志后，后端调用大模型 API，如果上游模型服务返回无效响应，或者返回内容无法被正确处理，那么在符合网关语义的情况下，使用 `502` 通常比 `400` 更合理。

例如：

```text
客户端
  ↓ 合法请求
FastAPI 服务
  ↓ 调用失败
大模型 API
```

此时问题发生在后端调用上游模型服务的过程中，并不是客户端提交的请求本身有问题。

不过，**模型调用失败不一定全部使用 502**：

- 上游返回无效响应：可以考虑 `502`。
- 上游暂时不可用：可以考虑 `503`。
- 上游响应超时：可以考虑 `504`，具体取决于系统架构。
- 后端自身发生未预期异常：通常使用 `500`。

状态码应结合失败原因和服务架构选择，不应只根据异常名称机械映射。

## 问题 6：request_id 对排查 AI 应用问题有什么帮助？

`request_id` 是用于唯一标识一次请求的标识符。它可以将同一次请求在不同处理阶段产生的日志关联起来，帮助开发者定位问题。

在 AI 应用中，一次请求可能经历以下过程：

```text
收到 HTTP 请求
      ↓
参数校验
      ↓
调用大模型 API
      ↓
解析 JSON
      ↓
Pydantic 结构校验
      ↓
业务校验
      ↓
返回 HTTP 响应
```

如果没有统一的 `request_id`，排查问题时可能需要根据时间、日志内容等信息猜测哪些日志属于同一次请求。

有了 `request_id`，可以在各个处理阶段记录相同的标识：

```text
request_id=abc123 阶段=api      收到日志分析请求
request_id=abc123 阶段=llm      开始调用模型
request_id=abc123 阶段=llm      模型调用超时
request_id=abc123 阶段=exception 异常类型=LLMServiceError
request_id=abc123 阶段=response HTTP状态码=504
```

通过检索 `abc123`，就可以快速还原这次请求的处理过程。

`request_id` 主要有以下作用：

1. **关联日志**：将 API、Service、模型调用和异常处理阶段的日志关联起来。
2. **定位故障**：判断问题发生在参数校验、模型调用、JSON 解析还是业务校验阶段。
3. **辅助排查**：便于分析模型超时、服务不可用、结构化输出异常等问题。
4. **支持后续扩展**：未来接入任务日志检索、运维知识库和 Agent 工具调用时，可以通过请求标识追踪一次完整的执行链路。

需要注意，`request_id` 应在请求入口生成或接收经过可信校验的外部标识，并传递到相关业务日志中。它不应包含 API 密钥、用户密码等敏感信息，也不能替代日志脱敏、访问控制和链路追踪机制。

对于当前项目，可以先为每次日志分析请求生成一个 `request_id`，并在模型调用、异常处理及最终响应中使用它，为后续构建调度系统运维 Agent 打好基础。
