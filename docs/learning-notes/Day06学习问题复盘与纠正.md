# Day 6｜学习问题复盘与纠正

## 一、今日学习核心

AI 应用不能只关注模型能否返回结果，还要关注结果是否符合业务要求。

从工程角度看，需要区分三个层次：

1. **结构正确**：输出是否符合 JSON 语法和 Schema 约束。
2. **业务合格**：输出内容是否合理、完整，是否满足业务要求。
3. **效果可评估**：是否通过固定测试集验证效果，能否发现问题和回归。

---

## 二、问题 1：为什么 Structured Output 之后还需要业务校验？

### 1. 我的回答

因为大模型回答具有随机性，不能保证回答的结果对用户一定有用。

### 2. 评价与纠正

回答方向正确，但还需要区分**结构正确**和**业务正确**。

Structured Output 主要约束输出的数据结构和格式，例如：

- 字段名称是否符合要求。
- 字段类型是否正确。
- 必填字段是否存在。
- 输出是否符合预期的数据结构。

业务校验则进一步检查结果是否满足实际业务要求，例如：

- 错误类型判断是否合理。
- 原因分析是否充分。
- 建议是否具体、可执行。
- 内容是否符合业务规则。

需要注意：大模型的输出不可靠，不只是因为随机性，还可能因为日志信息不足、模型理解错误或推理不准确。即使模型输出完全确定，也可能给出错误答案。

### 3. 示例

```json
{
  "error_type": "数据库连接失败",
  "possible_causes": [
    "系统异常",
    "配置问题"
  ],
  "suggestions": [
    "检查系统",
    "检查配置"
  ]
}
```

这个 JSON 的结构没有问题，但原因和建议过于笼统，不能有效帮助开发人员排障。

### 4. 建议记忆的完整答案

> Structured Output 可以约束大模型输出的数据结构，但不能保证输出内容一定正确或有业务价值。大模型可能受到随机性、输入信息不足和自身能力限制等因素影响，因此还需要进行业务校验，检查字段内容是否完整、是否符合业务规则，以及建议是否具有可操作性。

## 三、问题 2：JSON 能够成功解析，为什么仍然可能是不合格的结果？

### 1. 我的回答

回答结果不一定具有可用性。

### 2. 评价与纠正

回答正确，但可以进一步理解为：**JSON 解析成功，只能证明数据符合 JSON 语法，不能证明数据结构合格，更不能证明业务内容正确。**

需要理解以下三个层次。

| 检查层次 | 检查内容 | 示例 |
|---|---|---|
| JSON 解析 | 是否符合 JSON 语法 | 花括号、引号、逗号等语法是否正确 |
| Schema 校验 | 字段和数据类型是否符合约束 | `suggestions` 是否为数组，必填字段是否存在 |
| 业务质量校验 | 内容是否合理、完整、有用 | 建议是否能指导实际排障 |

### 3. 示例

下面的 JSON 可以成功解析：

```json
{
  "error_type": "",
  "possible_causes": [],
  "suggestions": []
}
```

但是，它没有提供任何有效的分析信息。

如果 Schema 规定了必填字段和正确类型，这个结果仍然可能不符合 Schema；即使 Schema 允许空字符串和空数组，它也可能不符合业务要求。

### 4. 建议记忆的完整答案

> JSON 解析成功只代表数据符合 JSON 语法，不代表字段完整，更不代表内容正确。即使通过 Schema 校验，模型仍然可能输出空内容、泛泛而谈的原因、错误的判断或不可执行的建议。因此，需要依次进行 JSON 解析、Schema 校验和业务质量校验。

### 5. 核心链路

```text
JSON 语法正确
      ↓
Schema 校验通过
      ↓
业务质量合格
```

**前一层通过，并不意味着后一层一定通过。**

## 四、问题 3：Prompt A 和 Prompt B 的核心区别是什么？

### 1. 我的回答

A 的规定非常宽松，回答的内容以及格式都没有限制，B 则相反。

### 2. 评价与纠正

回答基本正确，需要进一步理解两者在**约束的具体程度**上的区别。

Prompt A：

```python
PROMPT_A = """请分析下面的 Java 错误日志，返回 JSON。错误日志：{log_text}"""
```

它只提出了基本任务，但没有明确规定：

- JSON 必须包含哪些字段。
- 每个字段应该是什么类型。
- 原因和建议至少有多少条。
- 分析结果需要达到什么质量要求。

Prompt B 则明确了输出格式、字段、数量和内容要求，使模型更容易按照预期生成结果。

不过，严格 Prompt 不意味着模型一定能满足所有要求。它只是更清楚地表达了预期，仍然需要通过结构化输出、校验和测试来验证实际效果。

另外，**Prompt 中要求返回 JSON，不等于已经启用了 API 层面的 Structured Outputs**。两者是不同的约束机制。

### 3. 建议记忆的完整答案

> Prompt A 的任务描述比较宽泛，对输出结构、字段、内容和质量的约束不足；Prompt B 则明确规定了输出字段、数据形式、内容数量和质量要求，使模型更容易按照预期生成结果。但 Prompt 写得更严格，不代表输出一定可靠，还需要通过结构校验和固定测试集验证效果。

### 4. 工程上的理解

Prompt 优化不能只看文字是否更详细，而要看它是否让实际结果变得更稳定、更具体、更符合业务需求。

## 五、问题 4：为什么需要固定的测试日志？

### 1. 我的回答

控制变量，要在一群不确定答案中，筛选出质量较高的。

### 2. 评价与纠正

你的“控制变量”理解很好，后半句可以更精确。

固定测试日志主要有三个作用。

#### 作用一：公平比较

使用相同的输入，比较 Prompt A 和 Prompt B 的输出质量。

#### 作用二：回归测试

修改 Prompt、模型参数或业务代码后，重新测试，检查原本正常的能力是否退化。

#### 作用三：持续改进

记录评分、错误类型和失败情况，逐渐发现模型在哪些日志场景下表现不好。

如果两次调用使用不同日志，就很难判断质量差异究竟来自 Prompt，还是来自输入内容。

固定测试集能够让输入保持一致，从而更好地隔离变量。

不过，固定的 5 条日志只能作为入门评估集。实际项目还需要增加不同类型的日志、已知正确答案和人工评审，避免模型只对这几条样例表现良好。

### 3. 建议记忆的完整答案

> 固定测试日志可以控制输入变量，使不同 Prompt、模型参数或代码版本的测试结果具有可比性。通过对同一批日志进行重复评估，可以观察输出质量的变化，发现回归问题，并为后续优化提供依据。但测试集需要覆盖多种真实场景，不能仅凭少量样例就认定模型整体质量可靠。

## 六、今日复盘：需要建立的工程思维

### 第一层：结构正确

核心问题：

- JSON 能否成功解析？
- 字段和类型是否符合 Schema？
- 必填字段是否存在？

对应技术：

- JSON 解析
- Pydantic 数据模型
- Schema 校验
- Structured Outputs

### 第二层：业务合格

核心问题：

- 原因是否合理？
- 建议是否具体？
- 结果是否满足业务规则？
- 内容是否能够帮助开发人员解决问题？

对应技术：

- 业务规则校验
- 字段内容校验
- 空值和异常值检查
- 结果质量评分

### 第三层：效果可评估

核心问题：

- 有没有固定测试集？
- 修改 Prompt 后效果有没有改善？
- 是否出现回归？
- 评分是否能够反映真实质量？

对应技术：

- 固定测试集
- 自动化评估
- 回归测试
- 人工标注与参考答案
- 评估结果记录

### 三层之间的关系

| 层次 | 核心目标 | 关键问题 |
|---|---|---|
| Structured Output | 让输出结构更可控 | 数据格式是否符合要求？ |
| 业务校验 | 让结果满足基本业务要求 | 内容是否合理、可用？ |
| Evaluation | 用测试数据验证效果 | 修改之后，效果是否真的改善？ |

## 七、对当前 `score_analysis()` 的进一步理解

目前的 `score_analysis()` 主要根据原因数量、建议数量和错误类型长度进行打分。

这种方式适合入门练习，但存在一个问题：**数量和长度不等于正确性。**

例如，模型给出两条错误原因，也可能获得较高分数，但这两条原因未必符合实际日志。

后续可以逐步改进：

1. **增加正确性检查**：判断错误类型和日志内容是否匹配。
2. **增加参考答案**：为固定测试日志准备人工确认的预期结果。
3. **评估建议的可执行性**：判断建议是否具体，能否指导实际排障。
4. **记录评估结果**：对比不同 Prompt 或代码版本的得分和失败情况。
5. **增加测试场景**：覆盖数据库连接失败、SQL 未知列、Bean 初始化失败等不同类型的日志。

需要注意，参考答案不一定只有唯一的正确表述。对于可能存在多种原因的日志，应当允许合理的不同答案，并结合日志证据进行判断。

## 八、今日最终总结

今天真正需要掌握的不是复杂的术语，而是 AI 应用开发中的基本工程思维。

一个日志分析器不能只判断大模型是否成功返回结果，还需要依次判断：

1. **调用是否成功**：API 是否正常返回。
2. **格式是否正确**：结果能否解析，是否符合 Schema。
3. **业务是否合格**：分析是否合理，建议是否可执行。
4. **效果是否可靠**：是否经过固定测试集和回归测试验证。

可以用下面这条链路总结 Day 6：

```text
调用 LLM
   ↓
获得模型输出
   ↓
解析 JSON
   ↓
校验 Schema
   ↓
执行业务校验
   ↓
评估结果质量
   ↓
记录测试结果并持续改进
```

**我的学习结论：**

Structured Output 解决的是输出结构的可控性，业务校验解决的是基本业务要求，Evaluation 解决的是如何通过测试数据验证效果。

下一步不是把答案背得更复杂，而是把这些理解落实到日志分析器中，让程序能够区分“调用成功”“格式正确”和“结果真正有用”。
