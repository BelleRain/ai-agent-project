# 二、今天要掌握什么

今天重点掌握下面 4 个概念：

1. Prompt 约束不等于绝对可靠
2. JSON 可解析不等于字段完整
3. 结构化结果必须做校验
4. AI 应用需要最基本的评估数据

今天要开始形成这样的工程思路：

```text
模型输出
  ↓
JSON 解析
  ↓
字段校验
  ↓
结果质量检查
  ↓
通过 / 警告 / 失败
```

这和普通 Java 后端的思路其实非常接近：

```text
请求
  ↓
DTO
  ↓
参数校验
  ↓
业务校验
  ↓
业务处理
```

区别在于：

> LLM 的输出不是传统意义上的“可信输入”，所以除了 Schema 校验，还需要进一步做业务质量检查。

## 1. 定义结果校验函数

```python
from typing import List

from pydantic import BaseModel


class ErrorAnalysis(BaseModel):
    error_type: str
    possible_causes: List[str]
    suggestions: List[str]


def validate_analysis(result: ErrorAnalysis) -> List[str]:
    warnings = []

    if len(result.possible_causes) < 2:
        warnings.append("可能原因少于 2 条")

    if len(result.suggestions) < 2:
        warnings.append("解决建议少于 2 条")

    if len(result.error_type.strip()) < 3:
        warnings.append("错误类型描述过短")

    return warnings
```

这里要注意：

`Pydantic` 解决的是：

> **数据结构是否符合要求。**

而 `validate_analysis()` 解决的是：

> **虽然结构正确，但业务内容是否基本合格。**

例如：

```json
{
  "error_type": "数据库问题",
  "possible_causes": ["原因1", "原因2"],
  "suggestions": ["建议1", "建议2"]
}
```

从 Schema 的角度看，这个结果完全合法。

但从实际故障分析的角度看，它可能没有任何价值。

所以：

```text
Schema 校验 ≠ 业务质量校验
```

# 四、增加一个简单评分函数

继续增加：

```python
def score_analysis(result: ErrorAnalysis) -> int:
    score = 100

    if len(result.possible_causes) < 2:
        score -= 20

    if len(result.suggestions) < 2:
        score -= 20

    if len(result.error_type.strip()) < 3:
        score -= 20

    return max(score, 0)
```

这里的评分**不是科学的 AI 评测体系**。

今天只是为了理解：

> **我们可以把一些业务要求转换成可自动检查的规则。**

例如：

```text
满分：100

原因少于 2 条：-20
建议少于 2 条：-20
错误类型过短：-20
```

这样就可以让程序自动告诉我们：

```text
这次模型输出虽然成功了，但质量只有 60 分。
```

# 六、Prompt 对比实验

今天再做一个非常重要的实验：

---

## 1. Prompt A：宽松版本

```python
PROMPT_A = """
请分析下面的 Java 错误日志，返回 JSON。

错误日志：
{log_text}
"""
```

这个 Prompt 基本没有什么约束。

---

## 2. Prompt B：严格版本

```python
PROMPT_B = """
你是一名资深 Java 后端故障分析工程师。

请严格返回 JSON，字段如下：

{
  "error_type": "简洁的错误类型",
  "possible_causes": ["至少 2 条可能原因"],
  "suggestions": ["至少 2 条解决建议"]
}

要求：
1. 只返回 JSON
2. 不要 Markdown
3. 不要输出额外解释
4. 原因和建议必须是数组
5. 内容必须结合日志，不要泛泛而谈

错误日志：
{log_text}
"""
```

---

# 七、Prompt A / B 怎么比较

不要只看：

> “能不能返回 JSON。”

至少比较下面 4 项：

| 对比项        | Prompt A | Prompt B |
| ---------- | -------- | -------- |
| 是否能够解析     | 记录结果     | 记录结果     |
| 字段是否完整     | 记录结果     | 记录结果     |
| 原因是否具体     | 记录结果     | 记录结果     |
| 建议是否接近真实排障 | 记录结果     | 记录结果     |

例如：

```text
Prompt A
错误类型：系统异常
可能原因：未知
建议：检查系统

Prompt B
错误类型：数据库连接失败
可能原因：
1. MySQL 网络连接中断
2. 数据库连接池初始化失败

建议：
1. 检查数据库地址、端口及网络连通性
2. 检查数据库连接池配置及数据库服务状态
```

你真正需要观察的是：

> **Prompt 的约束是否让模型输出更加稳定、具体、可执行。**

# 十、建议再增加 warnings 输出

```python
def evaluate_logs(logs: list[str]) -> None:
    total_score = 0

    for index, log_text in enumerate(logs, start=1):
        print(f"\n===== 第 {index} 条 =====")
        print(log_text)

        try:
            result = analyze_log(log_text)

            score = score_analysis(result)

                    print("-", warning)
            else:
                print("结果通过基础质量检查")

        except Exception as exc:
            print("调用失败：", exc)

    if logs:
        print("\n平均分：", total_score / len(logs))
```

# 十一、今天最重要的理解

今天不要把重点放在“评分算法写得多复杂”。

真正需要理解的是：

## 1. 程序不报错 ≠ AI 结果正确

例如：

```text
API 调用成功
↓
JSON 解析成功
↓
Pydantic 校验成功
```

只能说明：

> **这个结果在形式上合法。**

并不能说明：

> **这个结果对用户有用。**

---

## 2. JSON 可解析 ≠ 业务质量合格

例如：

```json
{
  "error_type": "异常",
  "possible_causes": [
    "系统问题",
    "配置问题"
  ],
  "suggestions": [
    "检查系统",
    "检查配置"
  ]
}
```

这个 JSON 完全可以解析。

但对于 Java 后端工程师来说，它几乎没有排障价值。

所以需要：

```text
结构校验
+
业务规则校验
```
