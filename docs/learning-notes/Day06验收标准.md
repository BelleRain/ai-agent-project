# Day 6｜验收标准：Prompt 评估 + 结构化输出稳定性

**学习阶段：** 9 月｜LLM API / Python / Prompt / Structured Output  
**核心目标：** 让日志分析器不仅能够运行，还能够识别输出结果是否满足基本业务要求。

---

## 一、核心知识理解

### 1. Structured Output 与业务校验

- [ ] 理解 Structured Output 的作用：约束模型输出的数据结构，使其符合预先定义的 Schema。
- [ ] 理解结构化输出不等于业务结果正确。
- [ ] 能够解释为什么结构化输出之后仍然需要业务校验。
- [ ] 能够区分 JSON 解析、Schema 校验和业务质量校验。

**验收要求：**

能够独立说明以下三个层次的区别：

| 层次 | 核心问题 | 示例 |
|---|---|---|
| JSON 解析 | 数据是否符合 JSON 语法？ | 引号、逗号、花括号是否正确 |
| Schema 校验 | 字段、类型和约束是否符合定义？ | `suggestions` 是否为数组 |
| 业务质量校验 | 内容是否满足实际业务要求？ | 建议是否具体、可执行 |

**必须理解：**

> JSON 能够解析，不代表字段完整；字段符合 Schema，也不代表模型给出的内容一定正确。

### 2. Prompt 设计与对比

- [ ] 能够编写宽松的 Prompt A。
- [ ] 能够编写具有明确输出要求的 Prompt B。
- [ ] 能够比较两种 Prompt 在格式、字段完整性和内容质量方面的差异。
- [ ] 理解 Prompt 约束能够改善输出，但不能保证模型一定给出正确答案。
- [ ] 理解 Prompt 中要求返回 JSON，与通过 API 的 Structured Outputs 机制约束 Schema 并不是同一件事。

**验收要求：**

能够回答：

1. Prompt A 和 Prompt B 的核心区别是什么？
2. 为什么更严格的 Prompt 仍然需要测试？
3. 为什么不能只根据一次运行结果判断哪个 Prompt 更好？

### 3. 固定测试集与评估

- [ ] 理解固定测试日志的作用。
- [ ] 能够使用相同的日志比较不同 Prompt 的输出。
- [ ] 理解固定输入有助于控制变量和比较测试结果。
- [ ] 理解少量测试样例不能代表模型在所有场景下的表现。

**必须理解：**

> 固定测试集让不同版本的测试结果具有可比性，并帮助发现问题和回归，但测试集本身需要覆盖足够多的真实业务场景。

## 二、代码实现验收

### 1. 定义结构化结果模型

- [ ] 使用 Pydantic 定义 `ErrorAnalysis`。
- [ ] 包含 `error_type`、`possible_causes`、`suggestions` 三个字段。
- [ ] 理解每个字段的类型和业务含义。

参考结构：

```python
from pydantic import BaseModel


class ErrorAnalysis(BaseModel):
    error_type: str
    possible_causes: list[str]
    suggestions: list[str]
```

### 2. 实现业务校验函数

- [ ] 实现 `validate_analysis(result)`。
- [ ] 检查可能原因是否少于 2 条。
- [ ] 检查解决建议是否少于 2 条。
- [ ] 检查错误类型描述是否过短。
- [ ] 能够返回多个质量警告，而不是发现第一个问题就停止。

**验收要求：**

对于内容不完整的结果，程序能够指出具体问题；对于满足当前基础规则的结果，能够返回空警告列表。

### 3. 实现简单评分函数

- [ ] 实现 `score_analysis(result)`。
- [ ] 设置初始分数为 100 分。
- [ ] 按照预设规则扣分。
- [ ] 使用 `max(score, 0)` 避免出现负分。
- [ ] 理解当前评分只是规则评分，不代表模型回答的真实正确率。

**验收要求：**

能够解释评分规则，并验证不同输入会产生符合规则预期的分数。

### 4. 实现批量评估函数

- [ ] 准备至少 5 条不同类型的 Java 后端错误日志。
- [ ] 实现 `evaluate_logs(logs)`。
- [ ] 逐条调用 `analyze_log(log_text)`。
- [ ] 输出原始日志、错误类型、评分和质量警告。
- [ ] 对调用异常进行处理，避免单条失败导致整个批次立即中断。
- [ ] 统计总分和平均分。
- [ ] 正确处理空列表，避免除以零。
- [ ] 最好单独统计成功评估的日志数量，避免将调用失败的日志误算为 0 分。

**验收要求：**

能够通过一次批量运行，观察多条日志的分析结果、质量警告和总体评分。

## 五、工程思维验收

完成今天的学习后，应当能够理解以下流程：

```text
输入日志
   ↓
构造 Prompt
   ↓
调用 LLM
   ↓
解析结构化结果
   ↓
Schema 校验
   ↓
业务质量校验
   ↓
评分与警告
   ↓
批量统计和结果比较
```

需要明确：

1. API 调用成功，只代表请求正常完成。
2. JSON 解析成功，只代表数据符合 JSON 语法。
3. Schema 校验通过，只代表数据结构符合定义的约束。
4. 业务校验通过，只代表结果满足当前设置的业务规则，并不保证结论绝对正确。
5. 评分能够辅助比较结果，但评分规则本身也需要验证和完善。

## 七、今日最终达成目标

今天不要求建立完整的 AI 评测框架，也不要求证明模型输出绝对正确。

**真正的验收标准是：**

你能够把日志分析器从一个“调用大模型并返回结果”的程序，推进为一个能够进行基础结构校验、业务质量检查、规则评分和批量评估的 AI 应用。

这意味着你开始建立 AI 应用工程中的重要意识：

> 不仅要让模型生成结果，还要定义什么样的结果才值得被接受，并通过测试持续验证结果质量。
