# Day 8 - Prompt Experiment

## 练习一：Temperature 实验记录

## 1. 实验目标

使用同一条 Java 错误日志，分别设置 `temperature = 0、0.3、0.7、1.0`，观察模型输出在错误分类、原因数量、建议内容和 JSON 格式方面的变化。

测试日志：

```text
HikariPool-1 - Exception during pool initialization
```

## 2. 实验结果

| temperature | 错误类型 | 原因数量 | 建议数量 | 原因是否具体 | 建议是否重复 | JSON 是否稳定 |
|---|---|---:|---:|---|---|---|
| 0.0 | HikariCP 连接池初始化异常 | 4 | 4 | 是 | 无明显重复 | 是 |
| 0.3 | HikariCP 连接池初始化失败 | 4 | 4 | 是 | 无明显重复 | 是 |
| 0.7 | HikariCP 连接池初始化失败 | 4 | 4 | 是 | 无明显重复 | 是 |
| 1.0 | HikariCP 连接池初始化异常 | 5 | 5 | 是 | 存在部分语义重叠 | 是 |

## 3. 实验观察

1. 四组结果的错误分类基本一致，说明当前 Prompt 对错误类型的约束比较有效。
2. 随着 temperature 设置变化，原因和建议的措辞、细节及数量出现了差异，但输出长度不一定与 temperature 呈固定关系。
3. 四组结果均返回了合法 JSON，但合法 JSON 不代表所有原因都准确，也不代表建议都适用于当前故障。
4. 模型能够识别多种可能原因，但由于输入日志缺少完整异常堆栈，无法确定真正的故障根因。
5. 对于 Java 故障日志分析任务，应优先保证分类合理、建议可执行、结论有依据，而不是追求输出条数更多。

## 4. 当前结论

对于当前日志分析任务，较低的 temperature 可以作为稳定性实验的起点，但不能仅凭一次测试就确定最佳参数。后续需要使用多条固定测试日志、多次重复调用，并结合输出正确性和建议可执行性进行评估。

当前 Prompt 已经能够约束输出的基本结构和分析方向，但仍需要程序校验和业务规则，才能提高批量日志分析的可靠性。

## 练习二：固定 temperature 重复运行 3 次

### 1. 实验设置

- 测试日志：`HikariPool-1 - Exception during pool initialization`
- temperature：`0.3`
- 运行次数：3 次
- 观察内容：错误分类、原因数量、建议数量、输出格式及内容差异。

### 2. 实验结果

| 运行次数 | 错误分类 | 原因数量 | 建议数量 | JSON 格式 |
|---|---|---:|---:|---|
| 第 1 次 | HikariCP 数据库连接池初始化失败 | 5 | 5 | 正常 |
| 第 2 次 | 数据库连接池初始化失败 | 5 | 6 | 正常 |
| 第 3 次 | 数据库连接池初始化失败 | 5 | 6 | 正常 |

### 3. 实验观察

1. 三次运行使用相同的日志和 temperature，但输出内容并不完全一致。
2. 三次结果的错误分类基本一致，说明模型能够稳定识别当前日志的大致问题类型。
3. 原因和建议的具体表述有所不同，建议数量也发生了变化，说明固定 temperature 并不保证生成结果完全一致。
4. 三次输出均为合法 JSON，但格式正确不代表每条原因都准确，也不代表所有排查建议都适用于当前故障。
5. 部分建议需要结合实际技术条件判断，例如 `ping` 不能代替数据库端口测试，而连接池参数调整也不能代替根因排查。

### 4. 实验结论

相同的 temperature 不能保证模型每次输出完全一致。对于 Java 故障日志分析，应该重点关注错误分类的一致性、原因的合理性、建议的可执行性以及输出结构的稳定性，而不是单纯追求输出内容更长或建议数量更多。

后续应通过固定测试集、多次重复调用和明确的业务评价标准，逐步验证模型输出是否满足实际使用要求。

## 练习三：严格 Prompt 与宽松 Prompt 对比

### 1. 实验设置

使用相同的 Java 错误日志和 `temperature = 0.3`，分别测试严格 Prompt 和宽松 Prompt。

### 2. 实验结果

| 对比项目 | 严格 Prompt | 宽松 Prompt |
|---|---|---|
| 是否明确指定字段 | 是 | 否 |
| 是否明确约束原因和建议 | 是 | 否 |
| 是否成功通过 Pydantic 校验 | 此前测试成功 | 失败 |
| 失败原因 | — | 缺少 possible_causes 和 suggestions |
| 是否适合当前批量分析程序 | 更适合 | 需要增加输出约束 |

### 3. 实验观察

1. 严格 Prompt 明确规定了 `error_type`、`possible_causes` 和 `suggestions` 三个字段，模型输出更符合程序预期。
2. 宽松 Prompt 只要求返回 JSON，没有规定具体字段，模型返回的数据结构与 `ErrorAnalysis` 不一致。
3. JSON 语法正确不代表数据结构符合业务要求，Pydantic 可以发现缺少必填字段的问题。
4. 对于批量日志分析任务，不能只依赖模型自行决定输出结构，应当明确约束字段，并通过程序校验结果。

### 4. 实验结论

严格 Prompt 比宽松 Prompt 更容易满足当前程序的数据结构要求。Prompt 负责表达任务要求，Pydantic 负责验证字段和数据类型，两者配合可以减少不符合预期的输出。但 Pydantic 校验通过也不代表故障原因和解决建议一定正确，仍需要业务层面的质量评估。
